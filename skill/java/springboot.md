## 핵심 원칙

### 1. 아키텍처 / 레이어 분리

- Controller / Service / Repository 역할이 명확히 분리되어 있는가
- Controller에서 비즈니스 로직을 수행하지 않는가
- Service는 도메인 중심으로 구성되어 있는가 (단순 orchestration 지양)
- Repository는 persistence 역할만 수행하는가

---

### 2. API 설계

- RESTful 규칙을 따르는가 (URI, Method, Status Code)
- 요청/응답 DTO가 명확히 분리되어 있는가
- 엔티티를 직접 외부로 노출하지 않는가
- 페이징 / 필터링 / 정렬 규칙이 일관적인가

---

### 3. 도메인 모델링

- 엔티티에 의미 없는 setter가 존재하지 않는가
- 비즈니스 로직이 Service가 아니라 도메인에 위치하는가
- enum / value object를 적절히 사용했는가

---

### 4. 트랜잭션 관리

- @Transactional 위치가 적절한가 (Service 레벨)
- readOnly 트랜잭션이 적용되어 있는가
- 트랜잭션 범위가 과도하지 않은가
- DB 접근하지 않은 클래스 또는 메소드에 @Transactional 어노테이션을 사용하지 않는다.

---

### 5. 예외 처리

- 공통 예외 처리 Advice 시리즈 어노테이션(@ControllerAdvice, @ExceptionHandler)이 적용되어 있는가
- 비즈니스 예외와 시스템 예외가 구분한다
- 의미 없는 Exception throw를 사용하지 않는다
- 기본적으로 모든 커스텀 예외는 `RuntimeException`을 상속하여 정의한다.
- `RuntimeException` 사용 기준
  - 비즈니스 로직 검증 실패 (예: 유저 없음, 상태 불일치)
  - 클라이언트 요청 오류 (잘못된 입력값, 조건 불충족)
  - 복구 가능한 예외 (서비스 흐름 내에서 처리 가능)
- `Exception` (checked exception)은 사용하지 않는다.
  - 불필요한 try-catch 남발을 유도하므로 금지한다.
- `Throwable` 직접 상속은 금지한다.
  - JVM 레벨 에러(`Error`)까지 포함되어 위험함
  - 프레임워크 및 시스템 레벨 처리와 충돌 가능
- 메시지가 사용자/로그 목적에 맞게 구분되어 있는가

---

### 6. 의존성 및 구조

- 순환 참조가 발생하지 않는가
- 불필요한 Bean 주입이 존재하지 않는가
- 인터페이스가 과도하게 사용되지 않았는가

---

### 7. 성능 / 확장성

- N+1 문제가 발생하지 않는가
- 불필요한 DB 호출이 존재하지 않는가
- 캐싱 전략이 필요한 구간이 식별되었는가
- 대량 데이터 처리 시 배치/스트리밍 고려가 되었는가

---

### 8. 테스트

- 핵심 비즈니스 로직에 대한 테스트가 존재하는가
- 단위 테스트 / 통합 테스트가 적절히 구분되어 있는가
- 테스트 코드가 실제 사용 시나리오를 반영하는가
