# TypeScript 컨벤션

## 목적
이 문서는 프론트엔드와 백엔드를 포함한 여러 프로젝트에서 공통으로 적용할 수 있는 TypeScript 작성 기준을 정의합니다. 네이밍, import, 타입 선언, helper 분리, 결측값 처리, 주석 규칙을 일관되게 유지하는 것이 목적입니다.

## 핵심 원칙
- 타입, 데이터 출처, 의도가 사용하는 위치에서 드러나야 합니다.
- 기교보다 예측 가능한 구조를 우선합니다.
- 오케스트레이션과 순수 계산을 분리합니다.
- 값의 출처를 끝까지 추적 가능하게 유지합니다.
- 결측값은 무심코 숨기지 않습니다.

## 파일과 import
- 파일명은 `kebab-case`를 사용합니다.
- 변수와 함수는 `camelCase`, 타입과 클래스는 `PascalCase`, 상수는 프로젝트 규칙에 맞는 형태를 사용합니다.
- barrel export는 피하고 실제 파일 경로를 직접 import 합니다.
- 타입 전용 import는 `import type`을 사용합니다.
- 공용 설정과 상수는 명시적인 전용 모듈에 모으고 feature 파일에 흩뿌리지 않습니다.
- config, store, remote object를 읽을 때는 출처가 흐려지지 않도록 넓은 구조분해를 피합니다.

## 타입 선언 규칙
- 의미 있는 함수 타입이 이미 있다면 매개변수 타입보다 함수 변수 타입 선언을 우선합니다.
- callback 시그니처는 다시 쓰지 말고 재사용합니다.
- 미사용 매개변수도 `_` 접두사로 명시합니다.
- 기존 타입을 `Pick`, `Omit`, indexed access 등으로 파생할 수 있으면 새로 복제하지 않습니다.
- 커스텀 타입이나 인터페이스의 의도가 이름만으로 충분하지 않으면 문서화합니다.

## 함수와 helper
- 책임이 분명한 작은 이름 있는 함수를 선호합니다.
- 범위가 작고 단순한 값 집합은 enum보다 union 또는 객체 리터럴을 먼저 검토합니다.
- helper는 실제 재사용, 계약 경계, 복잡도 증가가 있을 때만 분리합니다.
- 결과를 사용하는 위치에서 멀리 떨어진 큰 명령형 조립 블록은 피합니다.

## 결측값 처리
- 옵셔널 값과 부재 상태는 명시적으로 처리합니다.
- `??`, `||` 같은 넓은 폴백으로 값 부재를 무심코 가리지 않습니다.
- empty, missing, invalid 상태의 차이가 중요하면 분기를 코드에 드러냅니다.

## 주석과 JSDoc
- export 함수, 유틸, 복잡한 타입, 외부 연동 경계는 필요할 때 JSDoc을 추가합니다.
- I/O 또는 외부 연동 경계는 `@description`을 사용합니다.
- 내부 helper나 export 유틸은 `@summary`를 사용합니다.
- 인라인 주석은 왜 필요한지, 어떤 경계를 지키는지 설명합니다.

## 리뷰 체크리스트
- 네이밍이 안정적이고 일관적인가
- import가 직접적이고 소유 경계가 분명한가
- 타입을 새로 복제하지 않고 재사용하는가
- helper가 보기 좋음이 아니라 실제 이유를 가지고 존재하는가
- 옵셔널 값과 결측 상태가 의도적으로 드러나는가
